# AI reliability: timeouts, per-user rate limits, telemetry

> **Python AI backend note (2026-11-19):** AI Coach chat and insights, voice meal parsing, meal photo analysis and speech transcription are generated by the Python AI backend (`ai-backend/`), not by Node; it still runs inside the same `AiUsageGate` (flag, burst limit, quota, refund rules). Timeouts and failure handling for chat are in `docs/ai/learning/02-python-only-ai-architecture.md`. Meal photo: the app waits 30 s, Node's HTTP timeout to Python is capped at 27 s and Python's Gemini deadline is 1.5 s shorter (`docs/ai/learning/05-python-meal-photo-analysis.md`). Coach insights: the app waits 25 s, Node's HTTP timeout to Python is capped at 22 s and Python's Gemini deadline is 1.5 s shorter; any failure still ends in deterministic insights (HTTP 200, cached 10 minutes, quota unit consumed), see `docs/ai/learning/06-python-coach-insights.md`. The Node Gemini client and executor that used to call the provider directly were **removed in Phase 8 (2026-11-19)**; the gate, per-user rate limits and telemetry sections below describe what is live, and the timeout section describes the Python path.

Every call that can reach Gemini (coach chat, coach insights, meal photo, voice meal) goes through one
choke point, `AiUsageGate.run` (`src/shared/ai/ai-usage.ts`). In order:

1. **Global per-IP limiter** (`app.ts`, unchanged): coarse flood protection for every route.
2. **Auth + validation**: invalid requests never reach the gate and cost nothing.
3. **Per-user burst limit** (`src/shared/ai/ai-rate-limit.ts`): in-memory, no database round trip.
4. **Feature flag + atomic daily quota** (PostgreSQL, Step 1).
5. **Python AI backend call under a hard timeout** (`PythonAiClient`, one request, no retry; Python applies its own shorter Gemini deadline and its primary/fallback model logic).
6. **Telemetry** row in `gemini_usage_events`, attributed to the authenticated user (`GeminiRuntimeService.recordExternalUsage`, called by `callPythonAi`).

## Timeouts

Node makes **one** HTTP request per AI call to the Python AI backend (`callPythonAi` in
`src/shared/ai/python-ai-call.ts`); only Python talks to Gemini. Node's HTTP deadline is always longer
than Python's Gemini deadline, so Python reports a provider timeout itself whenever it can (the exact
per-feature numbers are in the Python guides linked at the top). Properties:

- One request per call. There is no retry and no second request after a timeout.
- A timeout is the same safe response for every feature: HTTP 503, code `SERVICE_UNAVAILABLE`, message
  `AI request timed out. Please try again.` (`AiTimeoutError`, `src/shared/ai/ai-timeout.ts`). No model,
  key, URL or provider text is ever included.
- Charging is unchanged: the unit is consumed once the request reached Python (a timeout is billable) and
  refunded only for failures before dispatch (for example Python unreachable).
- Coach insights deliberately catch provider failures, including timeouts, and return deterministic
  fallback insights (HTTP 200, cached 10 minutes). That existing behaviour is preserved.

## Per-user rate limits

Keyed by `ai:<action>:<userId>` where the user id is the authenticated user. Not the IP address (users behind
one carrier NAT do not share a budget) and not any part of the access token (refreshing or re-issuing tokens
does not create a new budget).

| Action | Limit per user per 15 min |
| --- | --- |
| `coach_chat` (chat and insights regeneration share it) | 30 |
| `meal_photo` | 10 |
| `voice_meal` | 10 |
| `workout_generator` | 10 |

Rejections are HTTP 429, code `RATE_LIMITED`, message `Too many requests. Try again later.` (the same code and
text as the global limiters) plus `details.retryAfterSeconds`. A rejected request reserves no quota, creates
no conversation or message and calls no provider. Cached insight reads call no provider and are not counted.

### Limitation: in-memory counters and multiple instances

Counters live in the memory of one API process. With N instances (for example Render scaled out) each keeps
its own counters, so a user's effective burst budget is up to N x the limit, and counters reset when an
instance restarts or redeploys. The **daily AI quota is not affected**: it is an atomic PostgreSQL counter,
exact across instances, and remains the hard cap on spend. The burst limit is abuse protection, not billing.

To make it exact across instances without code changes elsewhere, implement `AiRateLimitStore` on a shared
store (Redis: `INCR key`, `PEXPIRE key windowMs` on the first hit) and pass it to `createAiRateLimiter`.
No Redis is required today.

Limits are code defaults. Making them environment-configurable needs `config/env.ts` and `container.ts`.

## Telemetry

`GeminiRuntimeService.recordExternalUsage` writes one `gemini_usage_events` row per successful Python-served
call, with the user id taken from the authenticated request (the gate's AsyncLocalStorage context, safe under
concurrency) and the operation type (`coach_chat`, `coach_insights`, `meal_photo`, `voice_meal`). The row
carries the model Python used, token counts and the cost computed from the admin-managed pricing table; a call
Python served with its backup model is flagged `FALLBACK_SUCCESS`. Failed calls and requests rejected before
the provider (rate limit, quota, kill switch, Python unreachable) record no row. Tested against real
PostgreSQL in `tests/integration/repositories/ai-telemetry.test.ts`.
