=====================================
1. PURPOSE
=====================================

This document provides the definitive, authoritative folder structure for the FitOnus platform. Every file created by an engineer or AI coding agent must reside in the correct location as defined here. This structure enforces Clean Architecture, Feature-First module organization, and strict separation of concerns. Deviation from this structure is prohibited without an architectural review and explicit approval.

=====================================
2. OVERVIEW
=====================================

FitOnus uses a monorepo structure with four top-level projects: mobile, backend, admin, and web. This document focuses on the mobile and backend projects, which are the primary development targets. The folder structure implements Feature-First Architecture where each application feature is a self-contained module with its own components, hooks, services, stores, types, and utilities.

The key organizational principle is: "If you need to add or modify a feature, you should only need to touch files within that feature's directory and the route definition."

=====================================
3. GOALS
=====================================

  - Every engineer should be able to locate any file in under five seconds by following the naming conventions.
  - Every new feature should follow the exact same internal structure, enabling muscle memory and reducing cognitive load.
  - Cross-feature dependencies should be immediately visible through import paths.
  - The folder structure should support independent feature development, testing, and deployment.
  - Global/shared code should be minimal and only contain truly cross-cutting concerns.

=====================================
4. FUNCTIONAL REQUIREMENTS
=====================================

  - The mobile project must use Expo Router's file-based routing convention in src/app/.
  - Feature modules must be completely self-contained in src/features/.
  - Shared UI components must reside in src/components/ui/ (atomic) and src/components/shared/ (composite).
  - Global services, stores, hooks, types, and utilities must be separate from feature-specific ones.
  - The backend must separate routes, services, repositories, middleware, AI, and database concerns into distinct directories.
  - Configuration files (ESLint, Prettier, TypeScript, etc.) reside at the project root.

=====================================
5. NON-FUNCTIONAL REQUIREMENTS
=====================================

  - No directory should contain more than twenty files. If it exceeds this, introduce subdirectories.
  - File names must use kebab-case.
  - Directory names must use kebab-case.
  - Index files (index.ts) may only be used as barrel exports for feature modules, never for logic.
  - Test files reside alongside the files they test with a .test.ts(x) suffix.
  - Platform-specific files use the .ios.tsx, .android.tsx, or .web.tsx extension.

=====================================
6. USER FLOW
=====================================

6.1 Developer Finding a File

  Question: "Where is the workout card component?"
  Answer: src/features/workouts/components/workout-card.tsx

  Question: "Where is the API call for logging a meal?"
  Answer: src/features/nutrition/services/nutrition-api.ts

  Question: "Where is the Zustand store for authentication?"
  Answer: src/features/auth/stores/auth-store.ts

  Question: "Where is the base Button component?"
  Answer: src/components/ui/button.tsx

  Question: "Where is the workout list screen?"
  Answer: src/app/(tabs)/workouts/index.tsx

  Question: "Where is the AI Coach service on the backend?"
  Answer: backend/src/ai/coach.ts

  Question: "Where is the database migration for the users table?"
  Answer: backend/src/database/migrations/001_create_users.sql

6.2 Developer Creating a New Feature

  1. Create a new directory under src/features/ with the feature name.
  2. Create subdirectories: components/, hooks/, services/, stores/, types/, utils/, constants/.
  3. Create the route file(s) under src/app/ in the appropriate route group.
  4. Create an index.ts barrel file in the feature root exporting the public API.
  5. Create corresponding backend files: route, service, repository.
  6. Create database migration if new tables are needed.

  - Atomic UI components (button, input, card) → src/components/ui/
  - Composite shared components (metric-card, trend-chart) → src/components/shared/
  - Feature-specific components → src/features/[feature]/components/
  - A component is "shared" if it is used by two or more features.
  - A component is "feature-specific" if it is used by only one feature.
  - If a feature-specific component later becomes shared, move it to src/components/shared/ and update all imports.

=====================================
10. SCREENS
=====================================

Screen placement rules:

  - All screens are route files in src/app/.
  - Screens are grouped by authentication state: (auth)/ for unauthenticated, (tabs)/ for authenticated.
  - Modal screens reside in (modals)/.
  - Each tab has its own directory with a _layout.tsx for stack navigation.
  - Dynamic routes use [param].tsx naming convention.
  - Screen files should be thin — they compose feature components and connect hooks.

=====================================
11. API REQUIREMENTS
=====================================

API file placement rules:

  - Route definitions → backend/src/routes/v1/[resource].ts
  - Business logic → backend/src/services/[domain]-service.ts
  - Database access → backend/src/repositories/[domain]-repository.ts
  - Request/response types → backend/src/types/api.ts
  - Validation schemas → inline in route files or in backend/src/utils/validation.ts
  - Each route file registers all CRUD operations for a single resource.

=====================================
12. DATABASE TABLES
=====================================

Database file placement rules:

  - Migration files → backend/src/database/migrations/[NNN]_[description].sql
  - Seed files → backend/src/database/seeds/[domain].sql
  - Database client → backend/src/database/client.ts
  - Model types → backend/src/types/models.ts
  - Migrations are numbered sequentially and never renamed or reordered after deployment.
  - Each migration file contains both the UP and DOWN SQL separated by a comment marker.

=====================================
13. AI REQUIREMENTS
=====================================

AI file placement rules:

  - Core AI logic → backend/src/ai/ (coach.ts, memory.ts, rag.ts, embeddings.ts)
  - Function definitions → backend/src/ai/functions/
  - Prompt templates → backend/src/ai/prompts/
  - Knowledge base documents → backend/src/ai/knowledge/[category]/
  - AI-related types → backend/src/types/ai.ts
  - Background AI jobs → backend/src/jobs/workers/
  - AI repository (memory, embeddings CRUD) → backend/src/repositories/ai-repository.ts

=====================================
14. ERROR HANDLING
=====================================

  - Error class definitions → backend/src/utils/errors.ts
  - Error handler middleware → backend/src/middleware/error-handler.ts
  - Mobile error boundary → src/components/shared/error-boundary.tsx
  - Mobile error state component → src/components/shared/error-state.tsx
  - Crash reporting service → src/services/crash-reporting.ts
  - Feature-specific error handling lives within the feature's hooks and services.

=====================================
15. EDGE CASES
=====================================

  - Circular dependencies between features: prohibited. If Feature A needs data from Feature B, both should depend on a shared type defined in src/types/.
  - Deep nesting: no directory should be nested more than five levels deep from src/.
  - Large feature modules: if a feature's components/ directory exceeds fifteen files, introduce subdirectories by concern (e.g., components/forms/, components/cards/, components/charts/).
  - Platform-specific files: use .ios.tsx, .android.tsx, .web.tsx extensions. The generic .tsx file serves as the default.
  - Test co-location: test files live next to the files they test (e.g., workout-api.ts and workout-api.test.ts in the same directory), EXCEPT for integration tests which live in backend/tests/integration/.

17. BEST PRACTICES
=====================================

  - When in doubt about where a file goes, consult this document.
  - Prefer creating a new feature module over adding to an existing one if the functionality is distinct.
  - Keep barrel exports (index.ts) limited to the feature's public API. Do not re-export internal implementation details.
  - Never place logic files directly in src/. Every file must be in a subdirectory.
  - Assets must be organized by type (images/, fonts/, animations/), not by feature.
  - Configuration files (.eslintrc, .prettierrc, tsconfig) belong at the project root, not in src/.
