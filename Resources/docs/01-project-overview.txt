1. PURPOSE
=====================================

This document serves as the definitive reference for the FitOnus platform. It establishes the product vision, technical boundaries, architectural philosophy, and operational principles that govern all engineering decisions across the mobile application, backend services, and AI subsystems. Every engineer, AI coding agent, designer, and stakeholder should read this document before contributing to the codebase. This document is the single source of truth for what FitOnus is, why it exists, and how it will be built.

=====================================
2. OVERVIEW
=====================================

FitOnus is a comprehensive AI-powered fitness, health, nutrition, and wellness platform developed by TuneOnus. The platform delivers a deeply personalized health experience through an intelligent AI Coach that learns from user behavior, adapts recommendations in real time, and provides evidence-based guidance across every dimension of physical wellness.

The platform consists of four primary subsystems:

  1. Mobile Application — A cross-platform React Native (Expo) application targeting iOS and Android, serving as the primary user interface.

  2. Backend API — A robust Node.js server built with NestJS, responsible for business logic, data orchestration, and API management.

  3. Database Layer — PostgreSQL with Supabase for relational data, real-time subscriptions, and authentication, extended with pgvector for AI embedding storage and semantic search.

  4. AI Engine — Powered by OpenAI's Responses API with function calling, Retrieval-Augmented Generation (RAG), and persistent AI memory to deliver contextual, conversational, and adaptive coaching.

The product targets health-conscious individuals ranging from beginners to advanced athletes who want a unified platform that replaces fragmented fitness apps, meal trackers, sleep monitors, and wellness journals with a single intelligent companion.

Product Tagline: "Your AI-Powered Wellness Companion"

3. GOALS
=====================================

3.1 Product Goals
-----------------
  - Deliver a premium, Apple Health / Google Fit quality mobile experience with fluid animations, dark/light mode support, and accessibility compliance.
  - Provide an AI Coach that feels as natural and helpful as a human personal trainer, nutritionist, and wellness advisor combined.
  - Unify workout tracking, nutrition logging, sleep analysis, weight management, recovery monitoring, and health data aggregation into a single coherent experience.
  - Enable users to achieve measurable health outcomes through personalized, adaptive, and science-backed recommendations.
  - Build a platform that scales from thousands to millions of users without architectural rework.

3.2 Engineering Goals
---------------------
  - Implement Clean Architecture with strict separation of concerns across presentation, domain, and data layers.
  - Adopt Feature-First Architecture where each feature is a self-contained module with its own components, hooks, services, types, and tests.
  - Enforce SOLID principles, DRY (Don't Repeat Yourself), and KISS (Keep It Simple, Stupid) across every module.
  - Achieve greater than ninety-five percent type safety through rigorous TypeScript usage with strict mode enabled.
  - Maintain sub-two-second cold start times on mobile and sub-two-hundred-millisecond API response times for standard endpoints.
  - Design the AI subsystem for extensibility — new capabilities (e.g., mental wellness, hydration tracking) should plug in without modifying core AI infrastructure.

3.3 Business Goals
------------------
  - Launch a minimum viable product within sixteen weeks of active development.
  - Achieve a four-point-five or higher App Store and Play Store rating within the first quarter post-launch.
  - Support a freemium model with premium AI features gated behind a subscription tier.
  - Enable white-label licensing of the platform for corporate wellness programs.

5. NON-FUNCTIONAL REQUIREMENTS
=====================================

5.1 Performance
  - Mobile app cold start: less than two seconds.
  - API response time (P95): less than two hundred milliseconds for standard endpoints.
  - AI response time (P95): less than three seconds for conversational responses.
  - Offline capability for core features (workout logging, meal logging).
  - Image loading: lazy loading with progressive rendering and caching.

5.2 Scalability
  - Horizontal scaling of backend services behind a load balancer.
  - Database connection pooling via Supabase.
  - Rate limiting on all public endpoints.
  - AI request queuing for high-traffic periods.

5.3 Security
  - JWT-based authentication with short-lived access tokens and long-lived refresh tokens.
  - Row-Level Security (RLS) on all Supabase tables.
  - Input validation and sanitization on every endpoint.
  - HTTPS-only communication.
  - Encrypted storage of sensitive data (tokens, health data) using expo-secure-store and MMKV encryption.
  - OWASP Top Ten compliance.

5.4 Reliability
  - Ninety-nine-point-nine percent uptime target.
  - Automatic retries with exponential backoff for transient failures.
  - Circuit breaker pattern for external service calls (OpenAI, Health Connect).
  - Comprehensive error logging and monitoring.

5.5 Accessibility
  - WCAG 2.1 AA compliance.
  - Screen reader support with proper accessibility labels.
  - Minimum touch target size of forty-four by forty-four points.
  - Color contrast ratios meeting AA standards.
  - Support for dynamic font scaling.

5.6 Internationalization
  - Architecture prepared for multi-language support (i18n).
  - Date, time, and number formatting based on user locale.
  - Metric and imperial unit system support.

6. USER FLOW
=====================================

6.1 First-Time User Journey
  1. User downloads FitOnus from App Store or Play Store.
  2. Splash screen displays with brand animation.
  3. Onboarding carousel introduces key features (three to four screens).
  4. User selects "Get Started" and chooses authentication method.
  5. Registration form collects email and password (or social auth).
  6. Onboarding wizard begins:
     a. Personal information (name, age, gender).
     b. Body metrics (height, current weight, goal weight).
     c. Activity level selection (sedentary, lightly active, active, very active).
     d. Fitness goals (lose weight, build muscle, improve endurance, general wellness).
     e. Dietary preferences (omnivore, vegetarian, vegan, keto, allergies).
     f. Health Connect / HealthKit permission request.
     g. Notification permission request.
  7. AI Coach introduces itself and summarizes the user's profile.
  8. User lands on the personalized Dashboard.

6.2 Returning User Journey
  1. User opens FitOnus.
  2. Biometric or PIN authentication (if enabled).
  3. Dashboard loads with today's summary, synced health data, and AI insights.
  4. User navigates to desired feature via bottom tab navigation.

6.3 Core Interaction Loops
  - Workout Loop: Browse/search exercises → Select or generate workout → Start workout → Log sets/reps → Complete workout → View summary → AI feedback.
  - Nutrition Loop: Scan barcode or search food → Log meal → View daily totals → AI recommendations.
  - AI Coach Loop: Open chat → Ask question or request plan → AI responds with context-aware advice → User acts on recommendation → AI remembers and adapts.
  - Progress Loop: View dashboard → Drill into specific metric → Analyze trends → Read AI insights → Adjust goals.

7.2 Architecture Patterns
--------------------------

  Clean Architecture Layers:
    1. Presentation Layer — React Native components, screens, and navigation. Contains no business logic.
    2. Domain Layer — Use cases, entities, and business rules. Framework-agnostic. Pure TypeScript.
    3. Data Layer — Repositories, API clients, local storage adapters. Implements domain interfaces.

  Feature-First Organization:
    Each feature (auth, workout, nutrition, etc.) is a self-contained module with its own:
      - components/ (UI elements specific to the feature)
      - screens/ (screen-level components)
      - hooks/ (custom React hooks)
      - services/ (API and business logic)
      - stores/ (Zustand slices)
      - types/ (TypeScript interfaces and types)
      - utils/ (feature-specific utility functions)
      - constants/ (feature-specific constants)

  State Management Strategy:
    - Server State: TanStack Query for all API data (caching, background refetching, optimistic updates).
    - Client State: Zustand for UI state, user preferences, and ephemeral application state.
    - Persistent State: MMKV for offline data, cached preferences, and non-sensitive local storage.
    - Secure State: Expo Secure Store for tokens, credentials, and sensitive health data.

7.3 API Design
--------------
  - RESTful API with consistent resource naming.
  - Versioned endpoints (e.g., /api/v1/).
  - JSON request and response bodies.
  - Standardized error response format: { error: { code: string, message: string, details?: object } }.
  - Pagination via cursor-based pagination for large datasets.
  - Rate limiting with token bucket algorithm.
  - Request validation using JSON Schema or Zod on the server.

7.4 Database Design
-------------------
  - PostgreSQL with Supabase-managed infrastructure.
  - Normalized schema design with strategic denormalization for read-heavy tables.
  - Row-Level Security policies on every table.
  - UUID primary keys generated server-side.
  - Soft deletes with deleted_at timestamp columns.
  - Audit columns (created_at, updated_at) on every table.
  - pgvector extension for AI embedding storage and similarity search.
  - Database migrations managed via Supabase CLI.

7.5 AI Architecture
-------------------
  - OpenAI Responses API as the primary inference engine.
  - Function calling for structured actions (create workout, log meal, query data).
  - RAG pipeline: user query → embedding generation → pgvector similarity search → context injection → LLM response.
  - AI Memory: conversation history stored per user, summarized at configurable intervals, with long-term preference extraction.
  - Context Window Management: sliding window with priority-based message selection (recent messages, relevant memories, user profile).

9.1 Base UI Components (Design System)
  - Button: Primary, secondary, outline, ghost, and destructive variants. Supports loading state, disabled state, icon placement (left/right), and size variants (sm, md, lg).

  - Toast: Non-intrusive notification component with success, error, warning, and info variants.

9.2 Shared Composite Components
  - MetricCard: Displays a single metric (e.g., steps, calories) with value, unit, trend arrow, and mini sparkline chart.
  - TrendChart: Full-width chart component for displaying metric trends over configurable time periods (day, week, month, year).
  - EmptyState: Illustrated placeholder for screens with no data, including action button and descriptive text.
  - ErrorBoundary: Catches and gracefully handles React component errors with retry functionality.
  - Header: Screen header with back navigation, title, and optional action buttons.

11. API REQUIREMENTS
=====================================

11.1 API Standards
  - Base URL: /api/v1
  - Authentication: Bearer token in Authorization header.
  - Content-Type: application/json for all requests and responses.
  - HTTP Methods: GET (read), POST (create), PUT (full update), PATCH (partial update), DELETE (remove).
  - Status Codes: 200 (success), 201 (created), 204 (no content), 400 (bad request), 401 (unauthorized), 403 (forbidden), 404 (not found), 422 (validation error), 429 (rate limited), 500 (internal server error).

11.2 Core Endpoints
  - POST   /api/v1/auth/register
  - POST   /api/v1/auth/login
  - POST   /api/v1/auth/refresh
  - POST   /api/v1/auth/logout
  - POST   /api/v1/auth/forgot-password
  - GET    /api/v1/users/me
  - PATCH  /api/v1/users/me
  - DELETE /api/v1/users/me
  - GET    /api/v1/dashboard/summary
  - POST   /api/v1/coach/chat
  - GET    /api/v1/coach/history
  - GET    /api/v1/workouts
  - POST   /api/v1/workouts
  - GET    /api/v1/workouts/:id
  - POST   /api/v1/workouts/:id/sessions
  - GET    /api/v1/exercises
  - GET    /api/v1/nutrition/meals
  - POST   /api/v1/nutrition/meals
  - GET    /api/v1/nutrition/foods/search

13.4 AI Model Configuration
  - Primary model: GPT-4o via OpenAI Responses API.
  - Embedding model: text-embedding-3-small (1536 dimensions).
  - Temperature: 0.7 for conversational responses, 0.3 for structured data generation.

15. EDGE CASES
=====================================

  - User logs workout with zero sets or reps — validate minimum input requirements.
  - User deletes account with active subscription — handle subscription cancellation flow.
  - Health Connect permission revoked mid-session — gracefully degrade and prompt re-authorization.
  - User logs future-dated entries — allow with warning, do not display in "today" views.
  - Extremely large conversation histories — implement automatic summarization and archival.
  - User switches between metric and imperial units — recalculate and re-display all stored values.
  - Concurrent modifications from multiple devices — implement optimistic locking with conflict resolution.
  - User uploads corrupt or oversized progress photos — validate file type, dimensions, and size before upload.
  - AI Coach receives ambiguous or nonsensical input — respond with clarifying questions rather than hallucinated answers.
  - App killed during active workout — persist workout state to MMKV for recovery on next launch.
  - Network restored after extended offline period — queue and batch-sync accumulated local changes.
  - User's timezone changes (travel) — adjust all time-based calculations and display.
  - Barcode scan returns no results — fallback to manual food search with helpful messaging.
  - Push notification token refresh — handle token rotation and server-side registration update.

17. BEST PRACTICES
=====================================

17.1 Code Quality
  - Write TypeScript with strict mode. Never use the "any" type unless interfacing with an untyped external library, and even then, create proper type wrappers.
  - Every function, hook, and component must have a clear, single responsibility.
  - Prefer composition over inheritance in component design.
  - Use named exports exclusively. Default exports are prohibited.
  - Keep files under three hundred lines. If a file exceeds this, decompose it.
  - Write self-documenting code with descriptive variable and function names. Comments should explain "why," not "what."

17.2 React Native Specific
  - Use React Native Reanimated for all animations. Never use the Animated API from React Native core.
  - Memoize expensive components with React.memo and expensive computations with useMemo.
  - Use useCallback for all callback functions passed as props.
  - Avoid inline styles. Use StyleSheet.create or the theme system for all styling.
  - Handle keyboard avoidance consistently using react-native-keyboard-controller.
  - Test on both iOS and Android simulators before merging any PR.

17.3 State Management
  - Server state (API data) must live in TanStack Query. Never duplicate server state in Zustand.
  - Zustand stores must be small and focused. One store per domain concern.
  - MMKV is for persistence only. Always hydrate Zustand from MMKV on app launch, not during renders.
  - Never store derived state. Compute it from source state using selectors.

17.4 API Design
  - Every endpoint must validate request body, query parameters, and path parameters.
  - Never expose internal IDs or implementation details in API responses.
  - Use consistent naming: plural nouns for resource collections, singular for individual resources.
  - Always include request ID in responses for debugging and support.

17.5 Security
  - Never log sensitive data (passwords, tokens, health data).
  - Always use parameterized queries. Never interpolate user input into SQL.
  - Validate and sanitize all user input on the server, regardless of client-side validation.
  - Implement rate limiting on all authentication endpoints.
